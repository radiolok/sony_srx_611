# ТЗ: SRXWIN-NG — современный инструментарий для Sony SRX-611

Sep 26, 2026 · @Артём

## 1. Назначение и границы работ

Цель — кроссплатформенный набор инструментов SRXWIN-NG, который полностью заменяет 16-битный Sony SRXWIN (1996) для работы с контроллером робота Sony SCARA SRX-611 на современном ПК (Windows 10/11, Linux) через USB-RS232. Оригинальные утилиты работают только под DOS/Win16 и не запускаются в 64-битных ОС.

**Результат проекта** — четыре поставляемых компонента:

1. `srx-link` — библиотека обмена с контроллером по RS-232 (протокол восстановлен реверсом).
2. `srx-cli` — консольные команды, эквивалентные SEND / RECALL / FILES / FDEL / HIST / MONIT.
3. `srx-lang` — компиляторы и декомпиляторы LUNA, POINT и PLC, байт-в-байт совместимые с оригиналами.
4. `srx-studio` — GUI: редактор программ, передача файлов, онлайн-мониторинг переменных, I/O, реле, текущей позиции и истории ошибок.

**Критерий успеха проекта:** на реальном SRX-611 выполняется полный цикл «написать .LUN/.PON/.PLC → скомпилировать → передать → запустить → снять состояние → считать обратно» без единого оригинального EXE, а результаты компиляции совпадают с оригиналом байт-в-байт на эталонном корпусе.

**Вне рамок:** модификация прошивки контроллера; поддержка NEC PC-98 (INI\_RS98); печать листингов на принтер (LUNAPR — только экспорт в PDF/текст, низкий приоритет); инсталлятор INSTALLE.

## 2. Исходные материалы

Основа для реверса — архив `SRXWIN.zip` (19 файлов, 1991–1996) и отчёт `SRXWIN_tools_report.md`. Исходные файлы кладутся в репозиторий в `vendor/srxwin/` только для чтения, с проверкой MD5 из отчёта в CI.

| Исходный EXE | Формат | Что делает | Замена в SRXWIN-NG | Приоритет |
| --- | --- | --- | --- | --- |
| SEND, RECALL, FILES, FDEL, HIST, MONIT, INI\_RS | DOS MZ, Borland C++ | Обмен с контроллером; общий модуль `rsfnc.c`, `messg.c` | `srx-link` + `srx-cli` | P0 |
| ANNUL | DOS MZ | Декомпилятор LUNA `.OBJ → .LUN` | `srx-lang` | P1 |
| DISPON | DOS MZ | Декомпилятор точек `.DAT/.CDT/.MDT` | `srx-lang` | P1 |
| DPLC | DOS MZ | Декомпилятор PLC `.COD → .PLC` | `srx-lang` | P1 |
| LUNNA | DOS MZ | Компилятор LUNA 5.0, 2 прохода, библиотеки `.LSF/.LIB` | `srx-lang` | P2 |
| POINT | DOS MZ | Компилятор точек `.PON/.CPN/.MPN` | `srx-lang` | P2 |
| PLC | DOS MZ | Компилятор PLC `.PLC → .COD` (≤ 32 КБ) | `srx-lang` | P2 |
| SRXMONIE | NE Win16, MFC | GUI, онлайн-мониторинг; сама говорит с контроллером для мониторинга | `srx-studio` + мониторинг в `srx-link` | P1 (протокол), P3 (UI) |
| SRXMONIE.HLP | WinHelp 3.x | Справка: команды LUNA/PLC, ошибки E001…E4310 | Документация в Markdown | P0 |
| LUNAPR | DOS MZ, Turbo C++ | Печать листингов | Экспорт в редакторе | P3 |

**Что уже известно (статус — гипотеза, подлежит проверке на этапе 1):**

- Линия: `9600, n, 8, 2` — строки `COM1:9600, n, 8, 2` и `COM2:9600, n, 8, 2` в SRXMONIE.EXE.
- Используется линия DSR («RS232C DSR timeout error. Check … cable disconnection») — кабель и адаптер должны иметь полноценные DTR/DSR/RTS/CTS.
- Сеанс начинается с ESC-кода («Cannot receive the first ESC code»); кадры содержат контрольную сумму; есть таймауты приёма/передачи.
- Диапазоны номеров типов программ: LUNA 0–89 и 100–180, PLC 90–93.
- Предел файла для передачи из GUI — 60 577 байт; OBJ и DAT ≤ 64 КБ; COD ≤ 32 КБ.
- Коды ошибок компиляторов: LUNA 2000–2089, POINT 2092–2133, PLC 3115–3120.

**Дополнительные источники:** дамп прошивки контроллера (`ROM1-C.bin`, таблица токенов LUNA @`0xD99D2`, диспетчер @`0xC5CC4`) и отчёты по ней — используются для сверки со стороны контроллера.

**Правовая рамка:** декомпиляция ведётся для достижения совместимости с оборудованием (п. 2 ст. 1280 ГК РФ). Код SRXWIN-NG пишется заново по спецификациям; копировать дизассемблированный код и строки справки Sony в исходники запрещено. Публикация в открытом доступе — отдельное решение заказчика после консультации с юристом.

## 3. Целевая архитектура и стек

Архитектура — монорепозиторий из независимых пакетов с единым ядром; GUI и CLI — тонкие оболочки над библиотеками. В отличие от SRXMONIE, которая запускала DOS-утилиты через .PIF, все вызовы — внутрипроцессные функции.

```
srxwin-ng/
  packages/
    srx_formats/   # парсеры/сериализаторы .OBJ .DAT .CDT .MDT .COD .CTR .KEE .HST
    srx_link/      # транспорт (serial / TCP / replay), кадры, сессия, команды
    srx_lang/      # лексеры, парсеры, кодогенерация, декомпиляторы LUNA/POINT/PLC
    srx_errors/    # справочник кодов ошибок контроллера и компиляторов
    srx_cli/       # команда `srx` с подкомандами
    srx_studio/    # GUI
  tools/
    fake_controller/  # эмулятор контроллера для тестов
    golden/           # скрипты прогона оригинальных EXE в DOSBox-X
    sniff/            # захват и разбор трафика RS-232
  re/                 # проекты Ghidra, заметки, карты функций
  docs/spec/          # PROTOCOL.md, FORMATS.md, LUNA.md, POINT.md, PLC.md
  corpus/             # эталонные исходники и бинарники, записи сеансов
  vendor/srxwin/      # оригиналы, read-only
```

| Слой | Решение | Почему |
| --- | --- | --- |
| Язык ядра | Python 3.12+, строгая типизация (`mypy --strict`) | Низкий порог входа для джунов, быстрые эксперименты при реверсе; скорости для 9600 бод и файлов ≤ 64 КБ достаточно |
| Последовательный порт | `pyserial`, абстракция `Transport` | Подмена на TCP (DOSBox-X nullmodem) и replay в тестах |
| Форматы файлов | Декларативное описание (`construct` или Kaitai Struct) | Одно описание для чтения и записи, годится как документация |
| Парсеры языков | Рукописный лексер + рекурсивный спуск | Нужны точные тексты и коды ошибок оригинала; генераторы парсеров это усложняют |
| CLI | `typer` | Автосправка, автодополнение |
| GUI | PySide6 (Qt 6) + QScintilla или QPlainTextEdit с подсветкой | Нативно на Windows и Linux, без браузера |
| Тесты | `pytest`, `hypothesis`, покрытие ядра ≥ 85 % | Property-based тесты для round-trip форматов |
| Сборка | `uv`, `ruff`, pre-commit, GitHub Actions / GitLab CI; дистрибутив — PyInstaller (Windows .exe) и wheel | Один файл для оператора |
| Реверс | Ghidra 11+ с Ghidra Server (загрузчики MZ и NE встроены), DOSBox-X с отладчиком, Win 3.11 в 86Box для SRXMONIE, `helpdeco` для HLP | Всё бесплатно, работа командой в одной базе |

**Инварианты архитектуры:**

- `srx_formats` и `srx_lang` не зависят от `srx_link`; все три не зависят от GUI.
- Любая операция с контроллером идёт через один класс `Session`, который сериализует доступ к порту и пишет журнал кадров.
- Команды делятся на классы опасности `READ`, `WRITE`, `MOTION`; класс указан в коде и проверяется в `Session` (см. раздел 8).
- Публичный API ядра синхронный; GUI вызывает его из рабочего потока (`QThread`).

## 4. Функциональные требования

Каждое требование имеет идентификатор (`LNK-*`, `CLI-*`, `FMT-*`, `LNG-*`, `GUI-*`) — на него ссылаются задачи, PR и тесты.

### 4.1 srx-link — обмен с контроллером

- **LNK-01.** Транспорты: физический COM/USB-UART, TCP (для DOSBox-X и эмулятора), replay из файла записи.
- **LNK-02.** Параметры линии настраиваются; по умолчанию — значения, подтверждённые на этапе 1 (ожидается 9600 8N2). Управление DTR/RTS и контроль DSR/CTS — как в оригинале.
- **LNK-03.** Кадровый уровень: сборка/разбор кадров, ESC-рукопожатие, контрольная сумма, повторы, таймауты — строго по `docs/spec/PROTOCOL.md`.
- **LNK-04.** Команды уровня приложения: список программ, чтение и запись файла по типу (O/D/C/P) и номеру (0–180), удаление, чтение истории ошибок, чтение и запись параметров (.CTR) и keep-реле (.KEE).
- **LNK-05.** Онлайн-команды SRXMONIE: чтение/запись INT, REAL, POINT, STRING, DATI, DATR, массивов; I/O и реле PLC; текущая позиция; статус задач; override; ON-LINE/OFF-LINE; точки останова.
- **LNK-06.** Все ответы об ошибках контроллера отображаются в типизированные исключения (`ChecksumError`, `ProgramRunningError`, `MemoryFullError` …) с числовым кодом.
- **LNK-07.** Журнал сеанса: каждый байт с направлением и меткой времени в формате, пригодном для replay (JSON Lines).

### 4.2 srx-cli — консольные команды

| Требование | Команда | Оригинал | Класс опасности |
| --- | --- | --- | --- |
| CLI-01 | `srx files` | FILES | READ |
| CLI-02 | `srx recall <type> [--decompile]` | RECALL | READ |
| CLI-03 | `srx hist [-o file.hst]` | HIST | READ |
| CLI-04 | `srx backup <dir>` — полная резервная копия всех программ, .CDT, .CTR, .KEE | нет | READ |
| CLI-05 | `srx monitor` — терминал | MONIT | READ |
| CLI-06 | `srx send <file> <type>` | SEND | WRITE |
| CLI-07 | `srx delete <type> \| --all` | FDEL | WRITE |
| CLI-08 | `srx restore <dir>` — восстановление из backup | нет | WRITE |
| CLI-09 | `srx compile / decompile` | LUNNA, POINT, PLC, ANNUL, DISPON, DPLC | — |

- **CLI-10.** Совместимый режим флагов: `srx compat SEND -P1 -T5 -RO -Ffile` принимает синтаксис оригинала — для старых bat-скриптов и сравнительных тестов.
- **CLI-11.** WRITE-команды требуют подтверждения или флага `--yes` и перед записью автоматически сохраняют текущую версию файла с контроллера.
- **CLI-12.** Коды возврата: 0 — успех, 1 — ошибка контроллера, 2 — ошибка связи, 3 — ошибка компиляции; `--json` для машинного вывода.

### 4.3 srx-formats — форматы файлов

- **FMT-01.** Чтение и запись `.OBJ .LIB .DAT .CDT .MDT .COD .CTR .KEE .HST` с гарантией round-trip: `write(read(x)) == x` для всего корпуса.
- **FMT-02.** Каждый формат описан в `docs/spec/FORMATS.md`: заголовок, версия, порядок байтов, контрольные суммы, ссылка на функцию в Ghidra, где это видно.
- **FMT-03.** Редактор параметров `.CTR` — только чтение до отдельного решения ведущего инженера.

### 4.4 srx-lang — языки

- **LNG-01.** Декомпиляторы (ANNUL, DISPON, DPLC): текстовый вывод совпадает с оригиналом с точностью до пробелов и переводов строк (CRLF).
- **LNG-02.** Компиляторы (LUNNA, POINT, PLC): выходной бинарник байт-в-байт равен оригиналу, включая режимы `-R` (без комментариев), `-C` (common), `-M` (memory card), библиотеки `.LSF → .LIB`.
- **LNG-03.** Диагностика: те же номера ошибок (2000–2133, 3115–3120) на тех же входах, плюс номер строки и столбца; сообщения — на английском и русском; формат `.ERR` как у оригинала.
- **LNG-04.** Кодировка исходников: чтение Shift-JIS/ASCII, запись в той же кодировке; редактор может работать в UTF-8, но конвертирует при компиляции.
- **LNG-05.** Грамматики LUNA 5.0, POINT 5.0, SRX PLC формализованы в EBNF в `docs/spec/`; таблица опкодов сверена с таблицей токенов прошивки @`0xD99D2`.
- **LNG-06 (желательно).** Языковой сервер LSP для LUNA — подсветка ошибок и автодополнение в VS Code.

### 4.5 srx-studio — GUI

- **GUI-01.** Редактор .LUN/.PON/.PLC с подсветкой, компиляцией по F7 и переходом к строке ошибки.
- **GUI-02.** Панель контроллера: статус связи, список программ (FILES), SEND/RECALL/DELETE перетаскиванием, backup/restore.
- **GUI-03.** Окна мониторинга по аналогии с SRXMONIE: переменные LUNA, реле PLC (std, keep, timer, counter, in, out, special), I/O, текущая позиция, статус задач, история ошибок с расшифровкой. Период опроса настраивается.
- **GUI-04.** Редактор точек: таблица P(n) с XYZR, Left/Right (форма руки), кнопка «взять текущую позицию».
- **GUI-05.** Справка по командам и кодам ошибок E001…E4310, переписанная своими словами по итогам разбора HLP.
- **GUI-06.** Интерфейс на русском и английском (Qt Linguist).

## 5. Методика реверса и эталонного тестирования

Главный принцип: оригинальные EXE — это оракул. Статический реверс в Ghidra даёт гипотезы, а истиной считается только то, что подтверждено прогоном оригинала и сравнением байтов.

### 5.1 Стенд

- ПК с USB-RS232 на FTDI FT232R или аналоге с полным набором линий (не CH340 без DSR). Распиновку кабеля к SRX-611 фиксирует ведущий инженер по документации контроллера и прозвонке.
- Пассивный сниффер: Y-отвод TX→RX и RX→RX на два отдельных USB-UART или логический анализатор на TTL-стороне MAX232 — чтобы видеть и данные, и линии DTR/DSR.
- DOSBox-X: COM1 проброшен либо в физический порт (`serial1=directserial realport:COM3`), либо в TCP (`nullmodem`) для работы с эмулятором. Проверить, что оригинальные SEND/FILES вообще работают через DOSBox-X — это первая задача этапа 0.
- 86Box с Windows 3.11 — для запуска SRXMONIE и записи онлайн-команд мониторинга.

### 5.2 Протокол: порядок работы

1. Статика. В Ghidra разметить общий модуль `rsfnc.c` в SEND.EXE (самый простой), затем перенести имена на остальные утилиты через Version Tracking / BSim. Искать от строк ошибок («Check sum error», «ESC code error») и от вызовов `_bios_serialcom` / `int 14h` / прямых `in/out` к портам `0x3F8`/`0x2F8`.
2. Динамика. Записать сниффером минимум по 3 сеанса на каждую команду оригинала (FILES, RECALL разных типов, HIST), с разным содержимым контроллера. Плюс негативные случаи: несуществующая программа, отключённый кабель, программа в работе.
3. Спецификация. Свести в `PROTOCOL.md`: формат кадра, алгоритм контрольной суммы, диаграмма состояний сеанса, таблица команд и ответов, таймауты. Каждое утверждение — со ссылкой на адрес в EXE и файл записи из `corpus/sessions/`.
4. Эмулятор. `fake_controller` проигрывает записанные ответы и ведёт простую модель памяти. Тест приёмки эмулятора: оригинальные SEND/RECALL/FILES в DOSBox-X работают с ним без ошибок.
5. Реализация `srx-link` против эмулятора, и только потом — против реального контроллера.

### 5.3 Форматы и языки: дифференциальное тестирование

- **Эталонный корпус.** Источники: (а) все программы, считанные с робота; (б) примеры из HLP и руководств; (в) ручные тесты — по одному файлу на каждое ключевое слово и каждый код ошибки; (г) сгенерированные фаззером по грамматике.
- **Golden-раннер.** Скрипт `tools/golden` запускает оригинальный LUNNA/POINT/PLC/ANNUL/DISPON/DPLC в безголовом DOSBox-X на каждом файле корпуса и сохраняет выход (.OBJ/.DAT/.COD/.ERR/текст) как эталон. Эталоны коммитятся, CI сравнивает с ними наш выход.
- **Порядок:** сначала декомпиляторы (они раскрывают формат и таблицу опкодов), затем компиляторы. Порядок языков: POINT (проще, данные) → PLC (ограниченный набор инструкций) → LUNA (самый большой).
- **Таблицы извлекаются скриптом, а не руками:** таблицы ключевых слов и опкодов из LUNNA/ANNUL выгружаются Ghidra-скриптом в YAML, из которого генерируется код. Сверка с таблицей прошивки @`0xD99D2` — автоматический тест.
- **Вещественные числа.** Особое внимание формату REAL и координат в .DAT: Borland C использует IEEE-754 и эмуляцию x87, но округление при парсинге строки (`atof`/`strtod` рантайма 1991 г.) может отличаться от Python. Расхождения в младшем бите — баг нашей реализации, а не допустимая погрешность.

### 5.4 Документирование находок

- Каждая находка в `re/notes/` имеет статус: **Гипотеза** (видно в дизассемблере) → **Подтверждено** (есть тест на оригинале или запись сеанса) → **В спецификации** (перенесено в `docs/spec/`, одобрено ведущим).
- Имена в Ghidra: `mod_func` (например `rs_send_frame`, `lun_emit_opcode`); адреса в заметках в формате `SEND.EXE:1A2B:0045`.
- Код реализации пишется по спецификации, а не переводом декомпиляции Ghidra строка в строку.
- Справка HLP разбирается `helpdeco` на этапе 0: это самый дешёвый источник семантики всех команд LUNA/PLC и кодов ошибок.

## 6. Этапы и приёмка

Первая полезная точка — конец этапа 2: программы можно считывать и заливать с современного ПК, а компилировать временно оригиналом в DOSBox-X. Сроки — оценка для команды из 4 джунов на полной занятости; ведущий инженер уточняет их после этапа 0.

| Этап | Содержание | Срок, нед. | Критерий приёмки (gate) |
| --- | --- | --- | --- |
| 0. Стенд и инфраструктура | Репозиторий, CI, Ghidra Server, DOSBox-X, кабель и сниффер, разбор HLP | 2 | Оригинальные FILES и RECALL из DOSBox-X работают с роботом; сделана полная резервная копия контроллера оригинальными средствами |
| 1. Протокол | Реверс `rsfnc.c`, запись сеансов, PROTOCOL.md, `fake_controller` | 3–4 | Оригинальные SEND/RECALL/FILES/FDEL/HIST без ошибок работают с эмулятором; спецификация одобрена ведущим |
| 2. srx-link + srx-cli | LNK-01…07, CLI-01…12 | 3 | `srx backup` → `srx restore` на реальном роботе даёт байт-идентичное содержимое; 100 циклов send/recall без сбоев |
| 3. Форматы и декомпиляторы | FMT-01…03, LNG-01 | 4 | 100 % файлов корпуса: round-trip и совпадение текста с ANNUL/DISPON/DPLC |
| 4. Компиляторы | LNG-02…05: POINT → PLC → LUNA | 6–8 | 100 % корпуса байт-в-байт; те же коды ошибок на негативных тестах; фаззинг 10 000 файлов без расхождений |
| 5. Онлайн-мониторинг | Реверс SRXMONIE, LNK-05 | 3–4 | Все окна мониторинга показывают те же значения, что SRXMONIE в 86Box |
| 6. srx-studio | GUI-01…06, сборка дистрибутивов | 4–6 | Приёмочный сценарий из раздела 1 выполняется на Windows 11 и Ubuntu 24.04 без оригинальных EXE |

Этапы 3 и 5 можно вести параллельно с 2; этап 6 начинается после стабилизации API этапа 2. Итого ориентировочно 16–20 недель календарно.

**При каждой приёмке этапа** сдаются: код с зелёным CI, обновлённые `docs/spec/*`, отчёт по покрытию корпуса, список открытых вопросов и демонстрация ведущему инженеру на стенде.

## 7. Роли и правила работы

Ведущий инженер владеет архитектурой, спецификациями и доступом к роботу; джуны ведут треки и отвечают за тесты своего трека.

| Роль | Зона | Ключевые результаты |
| --- | --- | --- |
| Ведущий инженер | Архитектура, ревью, стенд, безопасность, приёмка этапов | Распиновка кабеля, одобренные спецификации, решения по WRITE/MOTION |
| Джун A — «Линк» | Протокол, сниффер, `fake_controller`, `srx-link`, `srx-cli` | PROTOCOL.md, этапы 1–2 |
| Джун B — «Форматы» | Форматы файлов, декомпиляторы, golden-раннер | FORMATS.md, этап 3 |
| Джун C — «Компиляторы» | Грамматики, POINT/PLC/LUNA, фаззер | LUNA.md, POINT.md, PLC.md, этап 4 |
| Джун D — «Студия» | CI, справка из HLP, справочник ошибок, реверс SRXMONIE, GUI | Этапы 0, 5, 6 |

Если джунов меньше четырёх, треки берутся последовательно в порядке A → B → C → D.

### 7.1 Правила для активной команды

Инициатива приветствуется, но в рамках этих правил:

1. **Сначала спецификация, потом код.** Код обмена или компиляции без соответствующего раздела в `docs/spec/` не мержится.
2. **Никаких «улучшений» оригинала** до достижения паритета. Странное поведение оригинала воспроизводится и помечается `# QUIRK:` со ссылкой на заметку. Улучшения — только за флагом и после этапа 4.
3. **Каждый PR** ссылается на требование (`LNK-03` и т. п.), содержит тесты и не больше \~400 строк изменений. Мерж — после ревью ведущего или (для GUI и инфраструктуры) другого джуна.
4. **Таймбокс на тупик:** если за 4 часа нет прогресса в реверсе функции — вопрос в общий канал с адресом и тем, что уже проверено.
5. **Записи сеансов и эталоны не редактируются руками** — только перегенерация скриптом. Если тест с эталоном падает, правится наш код.
6. **Доступ к роботу** — по расписанию и правилам раздела 8; вся повседневная разработка — против эмулятора.

### 7.2 Ритм

- Спринты по 2 недели; в конце — демо на стенде и обновление спецификаций.
- Ежедневный статус текстом: что подтверждено, что опровергнуто, где застрял.
- Раз в неделю — «разбор дизассемблера»: один джун показывает свою функцию в Ghidra, ведущий даёт обратную связь.

## 8. Безопасность и риски

SRX-611 — промышленный робот с быстрыми осями, а запасных частей к нему нет: ошибка в протоколе может стереть параметры или вызвать движение. Правила ниже обязательны и частично зашиты в код (`Session`).

### 8.1 Работа с реальным контроллером

- **До первого подключения нового ПО** — полная резервная копия (все программы, .CDT, .CTR, .KEE) оригинальными утилитами; три копии в разных местах. Записать фото экранов параметров с пульта (TP), если он есть.
- **Класс READ** — разрешён любому участнику по расписанию стенда.
- **Класс WRITE** — только в присутствии ведущего, серво выключены, сначала на свободных номерах типов, не занятых рабочими программами. Запись .CTR и .KEE заблокирована в коде до отдельного решения.
- **Класс MOTION** (запуск программ, servo ON, изменение override и точек в работающей программе) — только ведущий или под его непосредственным контролем. Оператор с рукой на аварийной кнопке, рабочая зона огорожена, override ≤ 10 % при первых запусках. В `srx-cli` MOTION-команды требуют флага `--i-am-at-the-estop`.
- **Фаззинг протокола** — только против эмулятора. Отправка реальному контроллеру команд, не встречавшихся в записях оригинальных сеансов, запрещена.
- **Журнал стенда:** кто, когда, какая версия ПО, какие WRITE/MOTION-операции; лог `Session` прикладывается.

### 8.2 Риски

| Риск | Вероятность | Последствия | Мера |
| --- | --- | --- | --- |
| Потеря параметров робота (.CTR) из-за ошибочной записи | Средняя | Робот неработоспособен | Резервные копии, блокировка записи .CTR в коде |
| Оригинальные утилиты не работают через DOSBox-X (тайминги, DSR) | Средняя | Нет оракула для протокола | Ретро-ПК или ноутбук с настоящим COM и DOS; 86Box |
| Волятильная память контроллера: села батарея SRAM | Высокая для техники 1990-х | Потеря программ и параметров | Проверить батарею на этапе 0, резервная копия в первый же день |
| Компилятор LUNA окажется сложнее оценки | Высокая | Сдвиг этапа 4 | До готовности — вызов оригинального LUNNA через встроенный DOSBox-X как резервный бэкенд |
| Протокол мониторинга SRXMONIE сложно извлечь из NE/MFC | Средняя | Нет онлайн-окон | Сниффер на живом сеансе SRXMONIE в 86Box; сверка с обработчиком в прошивке |
| Джуны уходят в переписывание и «улучшения» | Высокая | Потеря сроков | Правила 7.1, gate-критерии, ревью ведущего |
